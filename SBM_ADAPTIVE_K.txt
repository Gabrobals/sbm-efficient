# SBM-Adaptive-K (SBM-Efficient) — Theory + Implementation Spec

## 0. Scopo
SBM-Adaptive-K estende SBM-Efficient introducendo **controllo dinamico del compute**: invece di usare un Top-K fisso, il modello sceglie **K(x)** in funzione dell’incertezza del routing.

Obiettivo: ottenere un tradeoff migliore tra **Accuracy** e **Compute/Latency** rispetto a:
- Random routing (K fisso)
- Static Top-K (K fisso)
- SBM learnable con K fisso

SBM-Adaptive-K deve dimostrare riduzione di FLOPs/latency **reali eseguiti** mantenendo accuracy comparabile.

---

## 1. Definizioni

### 1.1 Experts bank
Abbiamo N experts. Per ogni input x, il router produce logits z(x) ∈ ℝ^N e probabilità:
p_i(x) = softmax(z(x) / tau_router)

### 1.2 Entropia del routing
H(x) = - ∑_i p_i(x) log(p_i(x) + ε)

Proprietà:
- H(x) ~ 0 quando p è “one-hot” (router molto certo).
- H(x) massima quando p è uniforme (router incerto).

### 1.3 K dinamico
Definiamo una policy K(x) che dipende da H(x) (o da una proxy equivalente: max-prob, margin, ecc.).

Tre famiglie, in ordine di implementazione consigliato:
1) Threshold (hard, semplice, robusta)
2) Budgeted-K (constraint su compute medio)
3) Differentiable expectation (più complessa, opzionale)

---

## 2. Politiche di Adaptive-K

### 2.1 Threshold policy (v1 — consigliata)
Scegli K in base a soglie su H:

K(x) =
- K_min se H(x) < h1
- K_mid se h1 ≤ H(x) < h2
- K_max se H(x) ≥ h2

Esempio pratico:
- K_min = 1
- K_mid = 2
- K_max = 4

Note:
- K_max ≤ N
- Le soglie h1, h2 sono iperparametri (inizialmente fissi)

Vantaggio:
- Semplice, deterministica, facile da validare.
- FLOPs scendono davvero perché per molti x userai K=1 o K=2.

### 2.2 Budgeted-K policy (v2 — raccomandata dopo v1)
Obiettivo: rispettare un budget di compute medio:
E[K(x)] ≤ K_budget

Meccanismo:
- usa la threshold policy, ma aggiusta dinamicamente h1/h2 per rispettare K_budget su una finestra mobile.

Vantaggio:
- controlli direttamente il costo.
- stabilizza l’uso del compute nel tempo.

### 2.3 Differentiable expected compute (v3 — opzionale)
Invece di scegliere K hard, definisci un gate continuo:
g_i(x) ∈ [0,1]
e fai mixture pesata (ma attenzione anti-pattern: può diventare full compute mascherato).

Questa v3 è opzionale e va implementata solo se la v1/v2 mostrano limite.

---

## 3. Sparse execution (regola anti-pattern)
È vietato calcolare tutti gli experts e poi mascherare.

Con Adaptive-K:
- devi calcolare **solo** gli experts selezionati (Top-K variabile per sample/batch).

Se il tuo codice calcola outputs di tutti gli experts, la metrica FLOPs/latency è invalida e la run va marcata INVALID.

---

## 4. Metriche e logging (estensione schema)

Aggiungere ai metrics aggregati e per-run:

### 4.1 Metriche nuove (obbligatorie per Adaptive-K)
- final.k_mean : float
- final.k_std : float
- final.k_histogram : dict (chiavi: K possibili, valori: conteggi o percentuali)
- final.flops_per_sample_mean : float (se disponibile)
- final.latency_per_batch_ms : float (se disponibile)

### 4.2 Coerenza attesa
- active_modules_mean ≈ k_mean
- flops_executed deve correlare con k_mean (se k scende, flops scendono)
- se K è spesso 1, latency dovrebbe scendere (anche se non linearmente)

---

## 5. Criteri di successo (Acceptance Criteria)

### 5.1 Accuracy/Compute
Per MNIST (iniziale):
- Accuracy_mean(Adaptive-K) ≥ Accuracy_mean(static_topk_k2) − 0.003 (−0.3%)
- flops_mean(Adaptive-K) ≤ flops_mean(static_topk_k2) * 0.75 (≥ 25% riduzione)  [target minimo]
- latency_mean(Adaptive-K) < latency_mean(static_topk_k2)  [desiderato; non sempre garantito su CPU]

### 5.2 Controllo compute
- k_mean deve essere < 2.0 se K_min=1, K_mid=2, K_max=4 e le soglie sono sensate.
- k_histogram non deve collassare sempre su K_max (altrimenti non stai riducendo compute).

### 5.3 Robustezza statistica
- minimo 5 seed
- riportare mean±std
- postflight deve passare per tutte le run

## 6. Implementazione — Design & Interfaces

### 6.1 Nuovo modulo: AdaptiveKPolicy
File: src/routing/adaptive_k.py

Interfaccia consigliata:
- compute per-sample entropy H
- produce per-sample K
- produce per-sample indices Top-K

Pseudo-signature:

```python
from dataclasses import dataclass
import torch

@dataclass
class AdaptiveKConfig:
    k_values: list[int]          # es: [1,2,4]
    h_thresholds: list[float]    # es: [0.5, 1.2] (len = len(k_values)-1)
    eps: float = 1e-9

class AdaptiveKPolicy:
    def __init__(self, cfg: AdaptiveKConfig):
        self.cfg = cfg

    def entropy(self, p: torch.Tensor) -> torch.Tensor:
        # p: [B, N]
        eps = self.cfg.eps
        return -(p * (p + eps).log()).sum(dim=-1)  # [B]

    def k_from_entropy(self, H: torch.Tensor) -> torch.Tensor:
        # H: [B] -> K: [B] (int64)
        # threshold policy v1
        k_vals = self.cfg.k_values
        thr = self.cfg.h_thresholds
        # Example for 3 k_values: [1,2,4], thresholds [h1,h2]
        K = torch.full_like(H, fill_value=k_vals[0], dtype=torch.long)
        if len(k_vals) >= 2:
            K = torch.where(H >= thr[0], torch.tensor(k_vals[1], device=H.device), K)
        if len(k_vals) >= 3:
            K = torch.where(H >= thr[1], torch.tensor(k_vals[2], device=H.device), K)
        return K

    def topk_indices(self, logits: torch.Tensor, K: torch.Tensor) -> list[torch.Tensor]:
        # logits: [B, N], K: [B]
        # returns list of index tensors per sample to support variable-K execution
        idx_list = []
        for b in range(logits.size(0)):
            kb = int(K[b].item())
            idx = torch.topk(logits[b], k=kb, dim=-1).indices
            idx_list.append(idx)
        return idx_list
Nota: v1 può essere implementata per-sample. In v2 si può ottimizzare per-group di K (bucket per K uguale).

7.2 Execute sparse per-sample

File: src/models/experts.py

Implementare una funzione che:

itera sui sample in batch

esegue solo gli experts selezionati

aggrega outputs (somma pesata o media)

evita full compute

Pseudo:
def execute_sparse(self, x, idx_list, weights_list=None):
    # x: [B,...]
    outs = []
    for b, idx in enumerate(idx_list):
        xb = x[b:b+1]
        yb = 0
        for j, e_idx in enumerate(idx.tolist()):
            out_e = self.experts[e_idx](xb)
            w = 1.0 if weights_list is None else weights_list[b][j]
            yb = yb + w * out_e
        outs.append(yb)
    return torch.cat(outs, dim=0)
Nota: è OK essere “non ottimizzato” nella v1. Prima serve correttezza e misure.
